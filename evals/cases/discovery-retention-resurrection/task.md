A production cluster running Kaniop v0.18.0 with a `KanidmBackupSchedule` and remote retention keeps raising `KaniopBackupValidationFailures` for several minutes right after each retention pass. `kubectl get kanidmbackup` shows far more records in `phase: Invalid` than `Ready` (38 versus 12), all of them labeled `kaniop.rs/discovered=true`, each with a `Ready=False` condition whose message is the generic "manifest is unreachable or invalid" and a validation Job that failed with HTTP 404 `NoSuchKey` on the manifest. Deleting those records makes them come back on a later discovery scan, and the failure counter grows every day. The manifest keys involved belong to artifacts retention deleted days earlier: on 2026-10-15 a backup created on 2026-10-09 was removed by retention, a record for the same manifest key reappeared at 03:23:48, its validation failed with 404 at 03:23:51, and the alert fired from 03:26 to 03:34. The same sequence repeated on 2026-10-16 and 2026-10-17. Repository connectivity and credentials are healthy, and no recovery point is actually missing.

Fix the operator so this cannot happen. A `KanidmBackup` that retention deleted must not be recreated from a repository scan that was already in flight when the delete happened, and a manifest that is demonstrably absent must be handled differently from a manifest that could not be reached. Discovered records must not pile up in `Invalid` and must not keep firing the alert, while a `KanidmBackup` that a user authored themselves and whose manifest really is gone must stay a visible, counted failure. Records already parked in `Invalid` by the current behavior must recover without manual cleanup. Do not leave deletion unbounded, do not automatically delete records a user authored, do not weaken the existing suppression of manifest keys that are already cataloged, and do not change the retention policy to dodge the race. Add regression tests for the classification, the race, and any automatic cleanup you introduce, and update the backup documentation so the reported behavior, conditions, and metrics match the implementation.
