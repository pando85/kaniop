# Implementation plan: Retire the v0.11 KanidmPersonAccount CRD plural migration

Derived from: `spec.md` in the same change

## Repository findings

- `libs/crd-migration` is used only by `cmd/crd-migrator/src/main.rs`; `apply_crds.rs`
  imports nothing from it.
- Chart templates under `charts/kaniop/templates/crd-migration/` are the only users of
  `crdMigration` values. `crd-apply_test.yaml` mentions the migration only in test titles.
- The e2e Rust test `tests/e2e/test/crd_migration.rs` was skipped from normal e2e runs
  through `E2E_TEST_SKIPS` and shard skips in the Makefile.
- CRDs are generated by `cmd/crdgen` from `libs/{group,oauth2,person,service-account}/src/crd.rs`,
  `libs/backup-core/src/crd.rs` (re-exported by `libs/backup`), `libs/operator/src/kanidm/crd.rs`,
  and `libs/operator/src/kanidm/restore/legacy.rs`. Any CRD change also changes the committed
  `charts/kaniop/crds/crds.yaml`, which CI requires to stay regenerated.
- `.github/kind-cluster.yaml` maps host ports 80/443; the upgrade test no longer needs ingress,
  so it creates the Kind cluster without that config and can run beside other local clusters.

## Ordered implementation steps

1. Remove the migration code, chart pieces, and plural e2e test; make `apply-crds` fail on the
   legacy CRD and on naming conflicts; add unit and chart tests.
2. Update docs and the chart README with the minimum upgrade source.
3. Rework the upgrade scripts and workflow.
4. Run local verification, including the Helm script on a new Kind cluster.

## Dependencies and coordination

This change merges before #1120 (KanidmRadiusServer), which will be rebased onto it. #1120
edits `cmd/crd-migrator/src/apply_crds.rs` (new CRD in `generate_crds`), so its rebase conflict
is limited to that list and the expected CRD count.

## Risks and blast radius

- Users skipping the documented path from v0.10.x: mitigated by the fail-safe legacy CRD check.
- Argo CD applies `crds/` itself and the hook applies the same content with a different field
  manager. Both set identical values, so no conflict is expected; the Argo CD job checks it.

## Alternatives rejected

- Keeping the migration behind a disabled-by-default flag: keeps the maintenance cost.
- Keeping the old skip-on-naming-conflict behavior: it would let an upgrade from v0.10.x
  proceed with an unserved person CRD.
- Keeping `crdMigration` as an ignored schema key: hides stale configuration.
