## Historical phases

### Sep 2024–Nov 2025: incubation

Kaniop spent roughly 417 days between repository creation and the first non-beta release (`v0.1.0`, 2025-11-08). The project established declarative Kanidm cluster and identity-resource reconciliation and had e2e coverage before the first ordinary release.

### Nov 2025–Feb 2026: lifecycle and compatibility

The project added credential rotation, account-policy support, `kanidmName`, IPv6/configurable IP family and runtime Kanidm compatibility checking.

[Issue #636](https://github.com/pando85/kaniop/issues/636) was an important production-derived milestone: an external user reported a concrete Kaniop/Kanidm version-skew failure and verified that downgrading Kanidm resolved it. The report was converted into runtime compatibility detection in roughly 5.5 hours.

### May–Jun 2026: Kubernetes platform integration

Gateway API, `BackendTLSPolicy`, runtime classes, pod-security configuration, appearance customization, mail-sender orchestration and operator leader election expanded Kaniop from a domain-specific reconciler into a more complete Kubernetes-native operating layer.

### Jul 2026: migration safety

The v0.11 `KanidmPersonAccount` plural correction was treated as a data-safety migration rather than a destructive CRD replacement. The migration included Helm and Argo CD integration, idempotency, failure recovery and exact identity UUID preservation tests.

### Aug 2026: disaster recovery and observability

Backup/restore orchestration, data movement and richer operator metrics arrived, alongside a six-shard e2e layout. The backup/restore subsystem was still experimental. [PR #981](https://github.com/pando85/kaniop/pull/981) explicitly corrected documentation that had overstated production readiness.

At the analysis boundary, `Cargo.toml` still expressed a `1.10.0` compatible requirement, while `Cargo.lock` resolved `kanidm_client`, `kanidm_proto` and `kanidm_lib_crypto` to 1.11.1. Kaniop's build script intentionally read the lockfile version for `KANIDM_CLIENT_VERSION`.

The HA upgrade e2e dynamically derived the previous minor and current resolved dependency version, producing an effective **1.10.0 → 1.11.1** two-replica upgrade test with replication checks before and after the transition.

## Testing maturity

By this point Kaniop had accumulated evidence of operational-safety thinking that went beyond normal controller unit tests:

- N-1 HA upgrades with replication verification;
- migration tests for Helm and Argo CD;
- failure injection and resume;
- migration idempotency;
- exact Kanidm UUID preservation;
- e2e coverage for new lifecycle features;
- six e2e shards: `kanidm-core`, `kanidm-ha`, `kanidm-data`, `oauth2`, `resources`, `misc`.

The scaling of the test infrastructure was itself a project-maturity signal.

This showed that raw PR count was not a useful proxy for human community breadth.

However, the opposite conclusion — that only seven external PRs meant little external contribution — was also wrong. There were 80 issues, 20 owner-authored, and 58 issues remained after excluding the owner and Renovate. A number of these contained high-value operational knowledge from real deployments.

### Production knowledge as contribution

[Issue #687](https://github.com/pando85/kaniop/issues/687) documented 92 managed resources (45 groups, 40 OAuth clients, seven persons), controller latency distributions and a cascading failure mechanism involving periodic reconciliation load and Kanidm health probes. It led to configurable IDM reconciliation intervals in roughly 6.25 hours.

Other external reports and contributions exposed requirements around version skew, IPv6, Kubernetes naming restrictions, runtime classes, cert-manager rotation, sidecars, managed Secret metadata and SSA, and Kubernetes networking/Gateway integration.

The resulting conclusion was:

> Kaniop remained maintainer-led in architectural ownership and code review, but its operational knowledge base was already meaningfully community-derived.

## AI-assisted development

AI use was explicitly observable in repository history and project tooling:

- Copilot instructions;
- agent-oriented repository guidance;
- Claude/OpenCode traces in history;
- explicit AI co-author metadata;
- Forkline-authored PRs;
- GitHub operations through the ChatGPT/Codex connector.

The conservative measurable lower bound was 71 Forkline-authored merged PRs:

- **8.5% of all merged PRs**;
- **20.8% of non-Renovate merged PRs**.

This was not interpreted as "20.8% of the code is AI-generated". Git history did not support reliable source-line provenance, and human-authored work could also have been AI-assisted.

A notable development model had emerged:

**production user contributes evidence → agent implements candidate change → CI/e2e validates it → maintainer reviews and merges.**

## Architecture growth

The Cargo workspace grew from 11 members at `v0.1.0` to 16 members at the analysis boundary, about 45% growth.

The new members were concentrated in migration, backup and data-movement subsystems. This represented operational depth rather than a simple increase in domain resource types.

## Main risks at the snapshot boundary

1. **Backup/restore maturity:** substantial implementation existed, but production qualification was the largest missing lifecycle gate.
2. **Maintainer concentration:** implementation throughput had increased through AI and external production input, but architectural/review bus factor remained concentrated.
3. **Pre-1.0 API stability:** broad capability existed without a 1.0 stability commitment.
4. **Attribution uncertainty:** explicit bot/agent activity was measurable, but total AI assistance and production deployment count were not.
5. **Missing star time series:** official timestamped data existed but was not retrievable through the analysis connector used for this snapshot.

## Snapshot conclusion

The most useful description of Kaniop's evolution at this point was a transition from **representing Kanidm in Kubernetes** to **safely operating Kanidm over time**.

Technical implementation was concentrated, but production knowledge was increasingly community-derived, and AI/agent implementation had become a first-class part of the project's development process. The next major maturity threshold was production-qualified disaster recovery rather than simply adding more CRDs.
